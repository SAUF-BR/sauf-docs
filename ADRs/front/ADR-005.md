# ADR-005 - Estratégia de autenticação e armazenamento do token JWT

- Status: Aceito
- Decisores: Gabrielle
- Data: 2026-09-16
- História Técnica: ADR-005 da planilha "SAUF - ADRs"

## Contexto e Declaração do Problema

É necessário definir uma estratégia segura para armazenar e enviar o token JWT utilizado na autenticação dos usuários do SAUF BR. A solução deve permitir a persistência da sessão após recarregamentos da página e, ao mesmo tempo, reduzir riscos relacionados ao roubo do token e a ataques como XSS e CSRF.

Para isso, foi avaliado o uso de JWT armazenado em cookie HttpOnly, comparando essa abordagem com o armazenamento em `localStorage`/`sessionStorage` e a manutenção do token apenas em memória.

## Fatores da Decisão

- Resistência ao roubo do token por ataques XSS
- Proteção contra ataques CSRF
- Persistência da sessão entre recarregamentos da página
- Segurança no armazenamento do token
- Esforço de implementação
- Compatibilidade e alinhamento com o backend Java

## Opções Consideradas

- Cookie HttpOnly (definido pelo backend)
- `localStorage` / `sessionStorage`
- Token mantido apenas em memória (sem persistência)

## Resultado da Decisão

Opção escolhida: **Cookie HttpOnly**.

Essa abordagem foi escolhida porque impede que o token seja acessado diretamente pelo JavaScript da aplicação, reduzindo o risco de roubo do JWT em caso de XSS.

Como cookies são enviados automaticamente pelo navegador nas requisições, a abordagem exige medidas adicionais contra CSRF. Para reduzir esse risco, serão utilizadas configurações adequadas de `SameSite` e, quando necessário, mecanismos adicionais de proteção CSRF.

### Consequências Positivas

- O token não pode ser acessado diretamente por `document.cookie` ou pelo JavaScript da aplicação quando o cookie possui a flag `HttpOnly`
- Reduz o risco de roubo do JWT por scripts maliciosos injetados por XSS
- A sessão pode persistir entre recarregamentos da página sem necessidade de armazenar o token no estado do frontend
- Centraliza no backend o controle sobre criação, expiração e remoção do cookie

### Consequências Negativas

- Como o navegador envia cookies automaticamente, é necessário considerar e mitigar ataques CSRF
- Exige configuração adequada das flags `HttpOnly`, `Secure` e `SameSite`
- Exige alinhamento com o backend Java para definir criação, expiração e remoção do cookie durante login e logout
- Caso frontend e backend estejam em origens diferentes, será necessário configurar corretamente CORS e o envio de credenciais nas requisições

## Prós e Contras das Opções

### Cookie HttpOnly

Token definido pelo backend através do cabeçalho `Set-Cookie`, utilizando as flags `HttpOnly`, `Secure` e `SameSite`. O token não é manipulado diretamente pelo JavaScript do frontend.

- Bom, porque impede que scripts executados no navegador leiam diretamente o JWT
- Bom, porque permite manter a sessão entre recarregamentos da página
- Bom, porque o gerenciamento do token fica concentrado no backend
- Ruim, porque exige medidas adicionais de proteção contra CSRF
- Ruim, porque exige configuração e integração adequada entre frontend e backend

### localStorage / sessionStorage

Token armazenado diretamente pelo JavaScript do frontend após a autenticação.

- Bom, porque possui implementação simples e permite que o frontend acesse facilmente o token
- Bom, porque não é enviado automaticamente pelo navegador, reduzindo a exposição a CSRF baseado em cookies
- Ruim, porque qualquer JavaScript executado na mesma origem pode acessar o token, aumentando o impacto de uma vulnerabilidade XSS
- Ruim, porque o frontend passa a ser responsável pelo armazenamento e gerenciamento do token

### Token em memória (sem persistência)

Token mantido apenas no estado ou em uma variável da aplicação, sem ser persistido no navegador.

- Bom, porque o token não fica armazenado permanentemente no navegador
- Bom, porque reduz o tempo de exposição do token caso a aplicação seja fechada ou recarregada
- Ruim, porque o token é perdido ao recarregar a página
- Ruim, porque manter uma sessão persistente exigiria uma estratégia adicional, como um refresh token armazenado de forma segura
- Ruim, porque aumenta a complexidade do fluxo de autenticação

## Revisão de 28/10/2026

Revisão feita ao mover as ADRs para o `sauf-docs`, comparando com o código do `sauf-web-front` e com o `sauf-api`. **A implementação atual contradiz esta decisão** (pendência P-10 do `DECISOES.md` do backend).

- `src/lib/api/client.ts` lê o token de `localStorage.getItem('sauf:token')` e envia no header `Authorization: Bearer`. Isso é a opção que esta ADR rejeitou.
- O cliente não usa `withCredentials`, que é necessário para o navegador enviar o cookie HttpOnly.
- No backend, o login será próprio da API (D-55, [ADR-BE-002](../backend/ADR-BE-002.md)), ainda não implementado. Hoje toda requisição usa um usuário provisório fixo (`UsuarioLogado`).

Para seguir a decisão quando o login existir:
1. A API cria o cookie no `POST /auth/login` (`HttpOnly`, `Secure`, `SameSite`) e o remove no logout;
2. O CORS da API passa a aceitar credenciais para a origem do front, e entra a proteção contra CSRF;
3. No front, o `client.ts` troca o interceptor do `localStorage` por `withCredentials: true`.

Se o time preferir manter o Bearer em `localStorage`, esta ADR precisa ser substituída por uma nova, com o risco de XSS registrado.
